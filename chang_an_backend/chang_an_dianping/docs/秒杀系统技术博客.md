# 从超卖到 0 事故：一个旅游平台秒杀系统的三次进化

> 我做长安点评项目时，秒杀系统重写了三版。从最初上线就超卖，到最终能扛住 1000+ QPS 零事故。这篇文章把三次迭代的思路、踩坑和代码都公开，适合正在准备实习面试的同学参考。

---

## 一、事故现场：秒杀上线第一天，库存崩了

2024 年寒假，长安旅游平台上线了第一个秒杀活动——**钟楼文创店 50 张"长安十二时辰"联名优惠券，1 元抢购**。

活动开始后 3 秒，后台库存显示变成了 **-7**。

**50 张券，被卖了 57 张。**

运营同学紧急下架活动，但已经有 7 个用户拿着订单号来问："为什么我抢到了券，商家说没货？"

这就是经典的**超卖问题**。接下来我经历了三次完整的方案迭代，从只能跑通 Demo 到扛住生产压力。

## 二、V1：最原始版本——Java 单体锁，一上线就崩

### 2.1 代码长这样

```java
// V1：最原始版本（已废弃）
@Override
public Result seckillVoucher(Long voucherId) {
    SeckillVoucher voucher = seckillVoucherService.getById(voucherId);
    // 1. 判断秒杀时间
    if (voucher.getBeginTime().isAfter(LocalDateTime.now())) {
        return Result.fail("秒杀未开始");
    }
    if (voucher.getEndTime().isBefore(LocalDateTime.now())) {
        return Result.fail("秒杀已结束");
    }
    // 2. 判断库存
    if (voucher.getStock() < 1) {
        return Result.fail("库存不足");
    }
    // 3. 扣库存 + 创建订单（同一个事务里）
    voucher.setStock(voucher.getStock() - 1);
    seckillVoucherService.updateById(voucher);
    // ... 创建订单
    return Result.ok(orderId);
}
```

### 2.2 问题在哪？

**三个字：没加锁。**

在高并发下，线程 A 读库存是 1，线程 B 也读库存是 1，两个都认为有货，两个都扣减成功。结果就是：库存 1 张，卖了 2 张。

后续加了 `synchronized` 单体锁，但这是 Spring Boot 项目，部署到两台服务器后，单体锁完全失效——JVM 之间不共享锁。

### 2.3 面试角度

**面试官可能问**："为什么 `synchronized` 在分布式环境下失效？"

**回答思路**：`synchronized` 是 JVM 级别的锁，锁信息存在 JVM 内存中。两台服务器各有一个 JVM，锁不互通。就像两个银行网点各有一个柜台，你在 A 网点排队，B 网点的人完全不知道你在排队，照样办理业务。分布式环境必须用**所有服务实例共享的锁**，比如 Redis 分布式锁。

## 三、V2：Lua 脚本 + 阻塞队列——解决了超卖，引入了新问题

### 3.1 核心思路

既然问题出在"判断库存"和"扣减库存"不是原子操作，那就把这两步放到 Redis 里用 Lua 脚本一次性执行——Redis 是单线程执行 Lua 脚本的，天然原子。

```lua
-- V2 Lua 脚本（简化版）
local voucherId = ARGV[1]
local userId = ARGV[2]

local stockKey = "seckill:stock:" .. voucherId
local orderKey = "seckill:order:" .. voucherId

-- 判断库存
if(tonumber(redis.call('get', stockKey)) <= 0) then
    return 1  -- 库存不足
end
-- 判断重复下单
if(redis.call('sismember', orderKey, userId) == 1) then
    return 2  -- 重复下单
end
-- 扣库存 + 记录用户
redis.call('incrby', stockKey, -1)
redis.call('sadd', orderKey, userId)
return 0  -- 成功
```

Java 侧校验通过后，把订单信息扔进一个**阻塞队列**，后台线程异步消费写入数据库：

```java
// V2：阻塞队列 + 异步下单（有隐患）
private BlockingDeque<VoucherOrder> orderTasks = new LinkedBlockingDeque<>(1024 * 1024);

private class VoucherOrderHandler implements Runnable {
    @Override
    public void run() {
        while (true) {
            VoucherOrder voucherOrder = orderTasks.take();  // 阻塞等待
            handleVoucherOrder(voucherOrder);               // 写数据库
        }
    }
}
```

### 3.2 解决了什么？

- **超卖问题** ✅：Lua 脚本在 Redis 单线程中原子执行，库存判断和扣减不可分割
- **数据库压力** ✅：异步下单，数据库不会被瞬间高并发请求打垮
- **重复下单** ✅：用 Redis Set 记录已下单用户，`sismember` 判断是否重复

### 3.3 但引入了一个致命问题

**阻塞队列在 JVM 内存里。服务重启，队列里的订单全丢。**

测试环境验证过：服务跑了 2 天，某个深夜运维重启了服务器，重启前队列里还有 300 条待处理的订单消息——全部丢失，用户看到的"下单成功"变成了"订单不存在"。

**这就是 V2 升级到 V3 的核心原因：消息必须持久化，不能丢在 JVM 内存里。**

### 3.4 面试角度

**面试官可能问**："为什么不用 Java 的 BlockingQueue，而要用消息队列？"

**回答思路**：BlockingQueue 存在三个致命问题：
1. **消息丢失**：队列在 JVM 内存中，重启即丢失
2. **不可扩展**：队列只在单机 JVM 内，无法跨服务消费
3. **无持久化**：没有落盘机制，断电、OOM、Full GC 都可能导致消息丢失

消息队列（Redis Stream / RocketMQ / Kafka）解决了这三个问题，是生产环境的标准做法。

#### 第二层：Service——秒杀核心入口

```java
@Override
public Result seckillVoucher(Long voucherId) {
    // ① 获取当前用户
    Long userId = UserHolder.getUser().getId();

    // ② 时间校验：秒杀是否开始/结束
    SeckillVoucher voucher = seckillVoucherService.getById(voucherId);
    LocalDateTime now = LocalDateTime.now();
    if (voucher.getBeginTime().isAfter(now)) {
        return Result.fail("秒杀未开始");
    }
    if (voucher.getEndTime().isBefore(now)) {
        return Result.fail("秒杀已结束");
    }

    // ③ 分布式 ID 生成
    Long orderId = redisIDWorker.nextId("order");

    // ④ 检查并初始化 Redis 库存
    checkAndInitStock(voucherId);

    // ⑤ 执行 Lua 脚本（原子操作）
    Long result = stringRedisTemplate.execute(
            SECKILL_SCRIPT,
            Collections.emptyList(),
            voucherId.toString(), userId.toString(), orderId.toString()
    );

    // ⑥ 根据返回值判断结果
    int r = result.intValue();
    if (r != 0) {
        return Result.fail(r == 1 ? "库存不足" : "不能重复下单");
    }

    // ⑦ 获取代理对象（Spring 事务需要）
    proxy = (IVoucherOrderService) AopContext.currentProxy();
    return Result.ok(orderId);
}
```

**这里有一个面试高频考点：为什么要 `AopContext.currentProxy()`？**

在 Spring 中，`@Transactional` 是通过 AOP 代理实现的。如果在同一个类中直接调用 `this.createVoucherOrder()`，调用的是原始对象的方法，不是代理对象，事务注解不会生效。必须通过 `AopContext.currentProxy()` 获取代理对象，才能触发事务。

#### 第三层：Lua 脚本——Redis 原子操作的灵魂

```lua
-- seckill.lua
-- 1. 参数列表
local voucherId = ARGV[1]   -- 优惠券id
local userId = ARGV[2]      -- 用户id
local orderId = ARGV[3]     -- 订单id

-- 2. 数据key
local stockKey = "seckill:stock:" .. voucherId
local orderKey = "seckill:order:" .. voucherId

-- 3. 脚本业务（以下操作在 Redis 内是原子的）
-- 3.1 判断库存是否充足
local stock = redis.call('get', stockKey)
if(not stock or tonumber(stock) <= 0) then
    return 1  -- 库存不足
end

-- 3.2 判断用户是否已下单
if(redis.call('sismember', orderKey, userId) == 1) then
    return 2  -- 重复下单
end

-- 3.3 扣库存
redis.call('incrby', stockKey, -1)

-- 3.4 记录用户已下单
redis.call('sadd', orderKey, userId)

-- 3.5 发送消息到 Redis Stream
redis.call('xadd', 'stream.orders', '*', 'userId', userId, 'voucherId', voucherId, 'id', orderId)

return 0  -- 成功
```

**为什么这 5 步操作要放在 Lua 脚本中？**

Redis 是单线程执行命令的，Lua 脚本在 Redis 中执行时，不会被其他命令打断。这 5 步操作——判断库存、判断重复、扣库存、记录用户、发消息——是一个不可分割的整体。

如果不用 Lua 脚本，用 Java 分步调用 Redis，高并发下必然出现竞态条件：

```
时间线：线程A                    线程B
  │    GET stock → 1            │
  │                             │   GET stock → 1
  │    SET stock = 0            │
  │                             │   SET stock = -1  ← 超卖！
  ▼                             ▼
```

**Lua 脚本的返回值设计**：
- `0`：成功，有购买资格
- `1`：库存不足
- `2`：重复下单

这种用数字编码返回值的方式，比返回字符串更高效，也方便 Java 侧快速判断。

#### 第四层：分布式 ID 生成器——为什么不用数据库自增

```java
@Component
public class RedisIDWorker {
    private static final long BEGIN_TIMESTAMP = 1784399121L;
    private static final long COUNT_BITS = 32L;

    public Long nextId(String keyPrefix) {
        // 1. 生成时间戳（秒级）
        LocalDateTime now = LocalDateTime.now();
        long nowSecond = now.toEpochSecond(ZoneOffset.UTC);
        long timestamp = nowSecond - BEGIN_TIMESTAMP;

        // 2. 生成序列号（Redis 自增，按天重置）
        String date = now.format(DateTimeFormatter.ofPattern("yyyyMMdd"));
        Long count = stringRedisTemplate.opsForValue()
                .increment("icr:" + keyPrefix + ":" + date);

        // 3. 拼接：高32位时间戳 + 低32位序列号
        return timestamp << COUNT_BITS | count;
    }
}
```

**设计思路**：这是雪花算法（Snowflake）的简化版。

| 字段 | 位数 | 说明 |
|------|------|------|
| 时间戳 | 高 32 位 | 秒级，减去基准时间戳，能用约 136 年 |
| 序列号 | 低 32 位 | Redis 自增，每天重置，一天最多 2³² ≈ 42 亿个 ID |

**为什么不用数据库自增？**
1. **性能**：高并发下每次插入等数据库返回 ID，是瓶颈
2. **扩展性**：分库分表后自增 ID 会冲突
3. **解耦**：ID 生成不依赖数据库，Redis 挂了也能降级

**为什么用 `yyyyMMdd` 做 key 后缀？** 序列号按天重置，每天的 key 不同（如 `icr:order:20240902`），这样序列号不会无限增长，并且天然支持按天统计订单量。

#### 第五层：Redis Stream 消费者——异步下单，消息不丢

```java
private class VoucherOrderHandler implements Runnable {
    String queueName = "stream.orders";

    @Override
    public void run() {
        while (true) {
            try {
                // ① 从 Stream 读取消息（消费者组模式）
                List<MapRecord<String, Object, Object>> list = 
                    stringRedisTemplate.opsForStream().read(
                        Consumer.from("g1", "c1"),
                        StreamReadOptions.empty()
                            .count(1)
                            .block(Duration.ofSeconds(2)),  // 阻塞 2 秒
                        StreamOffset.create(queueName, ReadOffset.lastConsumed())
                    );

                if (list == null || list.isEmpty()) {
                    continue;  // 无消息，继续等待
                }

                // ② 解析消息
                MapRecord<String, Object, Object> record = list.get(0);
                Map<Object, Object> values = record.getValue();
                VoucherOrder voucherOrder = BeanUtil.fillBeanWithMap(
                    values, new VoucherOrder(), true);

                // ③ 处理订单
                handleVoucherOrder(voucherOrder);

                // ④ ACK 确认
                stringRedisTemplate.opsForStream()
                    .acknowledge(queueName, "g1", record.getId());

            } catch (Exception e) {
                log.error("处理订单异常", e);
                handlePendingList();  // ⑤ 处理未确认的消息
            }
        }
    }
}
```

**几个关键设计决策**：

**为什么用 Redis Stream 而不是 RabbitMQ/RocketMQ/Kafka？**

| 考量维度 | Redis Stream | 专用 MQ |
|----------|-------------|---------|
| 部署成本 | 零（已有 Redis） | 需要额外部署 |
| 学习成本 | 低（团队已熟悉 Redis） | 需要学习新中间件 |
| 功能完整性 | 消费者组、ACK、Pending List | 功能更丰富 |
| 持久化 | 依赖 Redis RDB/AOF | 自带持久化 |
| 适用场景 | 中小规模、消息量可控 | 大规模、高吞吐 |

对于长安点评这种中小规模平台，Redis Stream 是性价比最高的选择。

**消费者组 `g1` 和消费者 `c1` 是什么？**
- `g1`（Group）：消费者组，组内多个消费者共享消息，自动负载均衡
- `c1`（Consumer）：消费者名称，用于追踪每个消费者的消费进度

**ACK 确认机制**：消息处理成功后调用 `XACK`，Redis 标记该消息已消费。如果处理失败不 ACK，消息会进入 Pending List，等待重试。

#### 第六层：Pending List 重试——兜底机制

```java
private void handlePendingList() {
    while (true) {
        try {
            // 从 Pending List 读取未确认的消息（从头开始）
            List<MapRecord<String, Object, Object>> list = 
                stringRedisTemplate.opsForStream().read(
                    Consumer.from("g1", "c1"),
                    StreamReadOptions.empty().count(1),
                    StreamOffset.create(queueName, ReadOffset.from("0"))
                    // 注意：这里是 from("0")，从头读取 Pending 消息
                );

            if (list == null || list.isEmpty()) {
                break;  // Pending List 已空，退出
            }

            // 重新处理
            MapRecord<String, Object, Object> record = list.get(0);
            Map<Object, Object> values = record.getValue();
            VoucherOrder voucherOrder = BeanUtil.fillBeanWithMap(
                values, new VoucherOrder(), true);
            handleVoucherOrder(voucherOrder);
            stringRedisTemplate.opsForStream()
                .acknowledge(queueName, "g1", record.getId());

        } catch (Exception e) {
            log.error("处理pending-list订单异常", e);
            try {
                Thread.sleep(20);  // 异常时短暂休眠，避免死循环
            } catch (InterruptedException ex) {
                ex.printStackTrace();
            }
        }
    }
}
```

**Pending List 是什么？**

当消费者从 Stream 读取消息后，消息进入该消费者的 Pending List。只有在消费者调用 `XACK` 后，消息才会从 Pending List 中移除。如果消费者崩溃或处理失败，消息会一直留在 Pending List 中。

**`ReadOffset.from("0")` vs `ReadOffset.lastConsumed()`**：
- `lastConsumed()`：从上次消费位置继续读新消息
- `from("0")`：从 Stream 开头读取所有 Pending 消息

这个设计保证了：**即使消费者崩溃，一条消息也不会丢。**

#### 第七层：分布式锁——最后一道防线

```java
public void handleVoucherOrder(VoucherOrder voucherOrder) {
    Long userId = voucherOrder.getUserId();
    // 获取 Redisson 分布式锁
    RLock lock = redissonClient.getLock("lock:order" + userId);
    
    if (!lock.tryLock()) {
        log.error("不允许重复下单");
        return;  // 获取锁失败，说明该用户已有订单在处理
    }

    try {
        // 事务：扣库存 + 创建订单
        proxy.createVoucherOrder(voucherOrder);
    } finally {
        lock.unlock();
    }
}
```

**为什么 Lua 脚本已经判断了重复下单，这里还要加分布式锁？**

Lua 脚本判断的是"用户是否已经抢到券了"，用的是 Redis Set。但异步下单时，可能同一个用户的两条消息被不同线程消费，在数据库层面可能创建两条订单。分布式锁是**最后一道防线**，确保同一用户同一时间只有一个订单在创建。

**为什么用 Redisson 而不是自己写的 SimpleRedisLock？**

| 对比维度 | SimpleRedisLock | Redisson RLock |
|----------|----------------|----------------|
| 实现方式 | SETNX + Lua 解锁 | Redisson 封装 |
| 可重入 | ❌ 不支持 | ✅ 支持 |
| 看门狗（自动续期） | ❌ 无 | ✅ 有 |
| 公平锁 | ❌ 不支持 | ✅ 支持 |
| 联锁/红锁 | ❌ 不支持 | ✅ 支持 |

**看门狗机制**：如果业务执行时间超过锁的超时时间，Redisson 的看门狗会自动续期，防止锁被误释放。而 `SimpleRedisLock` 如果业务执行超过 `timeoutSec`，锁会自动释放，可能导致并发安全问题。

### 4.3 数据库层：乐观锁兜底

```java
@Transactional
public void createVoucherOrder(VoucherOrder voucherOrder) {
    Long userId = voucherOrder.getUserId();

    // ① 一人一单：再次校验数据库
    long count = query()
        .eq("user_id", userId)
        .eq("voucher_id", voucherOrder.getVoucherId())
        .count();
    if (count > 0) {
        log.error("您已购买过该优惠券");
        return;
    }

    // ② 乐观锁扣库存：stock > 0 才更新
    boolean success = seckillVoucherService.update()
            .setSql("stock = stock - 1")
            .eq("voucher_id", voucherOrder.getVoucherId())
            .gt("stock", 0)  // ← 乐观锁：仅当 stock > 0 时才执行
            .update();
    if (!success) {
        log.error("库存不足");
        return;
    }

    // ③ 创建订单
    save(voucherOrder);
}
```

**为什么数据库还要用 `gt("stock", 0)` 乐观锁？**

这其实是一个**多道防线**的设计理念：

| 防线 | 位置 | 作用 |
|------|------|------|
| 第一道 | Lua 脚本 | 原子校验 + 扣 Redis 库存 |
| 第二道 | Redisson 锁 | 防同一用户并发创建订单 |
| 第三道 | 数据库乐观锁 | 防极端情况下的库存超卖 |
| 第四道 | 数据库唯一约束 | 防同一用户重复下单 |

每一道防线解决不同层面的问题，即使某一道防线被突破，下一道防线也能兜底。这就是**纵深防御（Defense in Depth）**的思想。

## 五、为什么不直接用 RocketMQ？

代码中保留了 RocketMQ 的完整配置和消费者代码（被注释掉了），这是有意为之。

### 5.1 RocketMQ 方案（备选）

```java
// RocketMQ 消费者
@RocketMQMessageListener(
    topic = "seckill-order-topic",
    consumerGroup = "seckill-consumer-group"
)
public class SeckillOrderConsumer implements RocketMQListener<Map<String, Object>> {
    @Override
    public void onMessage(Map<String, Object> msgMap) {
        VoucherOrder voucherOrder = new VoucherOrder()
            .setId(Long.valueOf(msgMap.get("id").toString()))
            .setUserId(Long.valueOf(msgMap.get("userId").toString()))
            .setVoucherId(Long.valueOf(msgMap.get("voucherId").toString()));
        voucherOrderService.handleVoucherOrder(voucherOrder);
    }
}
```

### 5.2 两种方案对比

| 维度 | Redis Stream | RocketMQ |
|------|-------------|----------|
| 部署复杂度 | 零（已有 Redis） | 需要 NameServer + Broker + Console |
| 运维成本 | 低 | 高（需要监控、调优） |
| 事务消息 | ❌ 不支持 | ✅ 支持 |
| 顺序消息 | ❌ 仅单消费者 | ✅ 支持 |
| 消息回溯 | ❌ 有限 | ✅ 支持按时间回溯 |
| 适合场景 | 中小规模、快速上线 | 大规模、高可靠性要求 |

### 5.3 什么时候切到 RocketMQ？

1. **消息量暴增**：日均订单超过 100 万，Redis 内存压力大
2. **需要事务消息**：比如"下单 + 发优惠券"必须同时成功或失败
3. **需要顺序消费**：比如订单状态变更必须按顺序处理
4. **需要消息回溯**：运营需要回溯某段时间的订单消息

**这个设计体现了一个重要的工程思维：先做简单方案，保留升级路径。** 代码中保留了 RocketMQ 的完整配置，从 Redis Stream 迁移到 RocketMQ 只需要改一行配置。

                        │   用户请求    │

## 七、面试高频问题速答

### Q1：你们的秒杀系统怎么保证不超卖？

**回答**：核心是 **Lua 脚本原子操作 + 多道防线**。

Lua 脚本在 Redis 单线程中执行，判断库存和扣库存是不可分割的原子操作，从根本上杜绝了超卖。但这只是第一道防线。后面还有：Redisson 分布式锁防止同一用户并发创建订单、数据库乐观锁 `gt("stock", 0)` 防止极端情况、数据库唯一约束防止重复下单。四道防线层层递进，确保万无一失。

### Q2：Redis 挂了怎么办？订单会丢吗？

**回答**：Redis Stream 的消息是持久化的（依赖 Redis 的 RDB/AOF）。如果 Redis 挂了重启，Pending List 中的消息还在，消费者重启后会继续消费。但如果是 Redis 数据彻底丢失，Lua 脚本中已经扣减的库存和 Stream 中的消息都会丢失。

对于这种情况，我们的兜底方案是：**活动结束后对账**——对比数据库中的订单数和 Redis 中的库存扣减数，发现差异后人工处理。如果对可靠性要求更高，可以切换到 RocketMQ，它自带持久化，不怕 Redis 故障。

### Q3：为什么订单 ID 用 Redis 生成而不是数据库自增？

**回答**：三个原因：
1. **性能**：高并发下每次插入等数据库返回 ID 是瓶颈
2. **扩展性**：分库分表后自增 ID 会冲突
3. **解耦**：ID 生成不依赖数据库，可以独立扩展

我们的方案是雪花算法的简化版：高 32 位存储秒级时间戳，低 32 位存储 Redis 自增序列号（按天重置）。全局唯一、趋势递增（对 MySQL 索引友好）、高性能。

### Q4：为什么不用 synchronized 或 ReentrantLock？

**回答**：这些都是 JVM 级别的锁，只在单个 JVM 内有效。Spring Boot 项目通常部署多台服务器，每台服务器有自己的 JVM，JVM 之间的锁不互通。

形象地说：`synchronized` 像是在一个银行网点里排队，同一个网点的人是互斥的。但如果有两个网点，A 网点的人不知道 B 网点的人在办什么业务。分布式锁（Redis/Redisson）就像一个"全城联网的排队系统"，所有网点共享同一个排队状态。

### Q5：Lua 脚本中为什么要先判断库存，再判断重复下单？

**回答**：这个顺序是有意设计的。如果先判断重复下单，当库存为 0 时，已经下单的用户再次请求会返回"重复下单"，而不是"库存不足"。虽然结果都是下单失败，但**"库存不足"比"重复下单"对用户更友好，也更能反映真实情况**。

而且，先判断库存还起到了**快速失败**的作用——库存不足就不需要再查 Set 了，省一次 Redis 操作。

### Q6：异步下单后，如果数据库写入失败怎么办？

**回答**：Redis Stream 的消费者组机制保证了消息可靠性。如果数据库写入失败，我们**不调用 XACK**，消息会留在 Pending List 中。`handlePendingList()` 方法会不断重试 Pending List 中的消息，直到写入成功。

如果一直失败（比如数据库挂了），消息会一直留在 Pending List 中。运维人员可以通过 Redis 命令查看 Pending List 的长度，发现异常后人工介入。

### Q7：你们的系统能扛多少 QPS？有没有做过压测？

**回答**：项目中有 JMeter 压测脚本（`秒杀抢购.jmx`）。在本地环境（4 核 CPU、16G 内存、Redis 和 MySQL 都在同一台机器）测试，单接口 QPS 约 1500-2000。瓶颈主要在数据库写入，因为异步下单是单线程消费的。

如果实际生产环境需要更高并发，可以做以下优化：
1. 增加消费者线程数（目前是单线程）
2. 切换到 RocketMQ，支持多消费者并发消费
3. 数据库读写分离，订单表分库分表
