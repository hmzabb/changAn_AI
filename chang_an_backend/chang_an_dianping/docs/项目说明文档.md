## 二、核心业务模块

### 2.1 用户模块

**涉及文件：**
- `controller/UserController.java`
- `service/impl/UserServiceImpl.java`
- `utils/RefreshTokenInterceptor.java`
- `utils/LoginInterceptor.java`
- `config/MvcConfig.java`
- `utils/UserHolder.java`

**功能清单：**

- 手机号 + 验证码登录（验证码存 Redis，2 分钟过期）
- 基于 Token 的会话管理（Redis Hash 存储，有效期约 6 小时）
- **双拦截器链**：`RefreshTokenInterceptor`（order=0，刷新 Token 有效期）→ `LoginInterceptor`（order=1，拦截未登录请求）
- 用户签到（Redis Bitmap 实现，支持连续签到天数统计）
- 用户信息查询

**关键设计：为什么用双拦截器？**

`RefreshTokenInterceptor` 的 order 为 0，先于 `LoginInterceptor` 执行。它的职责是"只要有 token 就刷新有效期并放行"，而 `LoginInterceptor` 负责"没有用户信息就拦截返回 401"。这样设计的好处是：
- 用户每次请求都会自动续期 Token，不需要手动刷新，保证了良好的用户体验
- 两段式拦截器比单段更灵活——你可以让某些接口（如商铺浏览、热门笔记）不需要登录也能访问，而 AI 接口、下单接口等必须登录
- `RefreshTokenInterceptor` 最后在 `afterCompletion` 中清除 ThreadLocal，防止内存泄漏

**MvcConfig 拦截器配置：**

```java
registry.addInterceptor(new LoginInterceptor())
    .excludePathPatterns(
        "/shop/**",          // 商铺浏览无需登录
        "/shop-type/**",     // 商铺类型无需登录
        "/voucher/**",       // 优惠券查看无需登录
        "/upload/**",        // 上传无需登录
        "/blog/hot",         // 热门笔记无需登录
        "/user/login",       // 登录接口本身
        "/user/code",        // 获取验证码
        "/user/info"         // 用户信息
    ).order(1);
registry.addInterceptor(new RefreshTokenInterceptor(stringRedisTemplate)).order(0);
```

### 2.2 商铺模块（缓存核心）

**涉及文件：**
- `controller/ShopController.java`
- `service/impl/ShopServiceImpl.java`
- `utils/CacheClient.java`
- `utils/BloomFilterInitializer.java`
- `utils/RedisData.java`
- `utils/RedisConstants.java`

**功能清单：**
- 商铺 CRUD（增删改查）
- 按类型分页查询 + Redis GEO 地理位置排序
- 按名称关键字搜索
- 缓存策略：**布隆过滤器 + 空值缓存** 防穿透，**逻辑过期** 防击穿，**TTL 随机化** 防雪崩

**核心设计：缓存三大问题的业务解法**

这是整个项目技术含量最高的模块。`CacheClient` 是一个通用的缓存工具类，封装了三种缓存策略：

#### 2.2.1 缓存穿透 → 布隆过滤器 + 空值缓存双保险

**为什么需要？** 如果有人用爬虫批量请求 `id=-1`、`id=999999` 这种不存在的商铺 ID，每次请求都会穿透 Redis 打到 MySQL，数据库瞬间被打满。

**方案：**
1. **第一道防线：布隆过滤器**。`BloomFilterInitializer` 通过 `ApplicationRunner` 在项目启动时自动加载所有商铺 ID 到布隆过滤器（预计 10 万条，误判率 1%）。查询时先过布隆过滤器，不存在直接返回 null，拦截 99% 的无效请求。
2. **第二道防线：空值缓存**。布隆过滤器有 1% 误判率，空值缓存兜底（缓存空字符串，TTL 2 分钟），防止那 1% 的误判请求穿透到数据库。

**为什么不只用空值缓存？** 如果只用空值缓存，恶意攻击者用随机 ID 刷接口，会生成大量空 key 占用 Redis 内存。布隆过滤器用极小内存（100 万数据只要几 MB）就能拦截绝大部分请求。

#### 2.2.2 缓存击穿 → 逻辑过期（非阻塞方案）

**为什么需要？** 热点商铺（如钟楼、回民街）缓存过期瞬间，大量请求同时打到 MySQL，数据库连接池被打满，所有接口超时。

**方案：** 逻辑过期——缓存不设物理 TTL（Redis 不自动删除），而是存储一个逻辑过期时间：
- 过期了也**先返回旧数据**给用户，保证用户不等待
- 只让**一个线程**获取互斥锁，异步去重建缓存
- 其他线程直接用旧数据，完全不阻塞

**为什么选逻辑过期而不是互斥锁？** 旅行点评平台的核心是"让用户流畅地浏览商铺"。如果用互斥锁，缓存过期时 1999 个用户要等待几百毫秒才能拿到响应，页面会卡顿。逻辑过期能立刻返回旧数据，用户感知不到任何延迟。商铺信息（名称、地址、评分）不会频繁变更，返回 30 秒前的旧数据对用户决策几乎没有影响。

#### 2.2.3 缓存雪崩 → TTL 随机化

**为什么需要？** 如果运营一次性导入 1000 个新商铺，统一设 30 分钟 TTL，30 分钟后所有缓存同时过期，数据库瞬间承受 10 倍压力。

**方案：** 设置缓存时在 TTL 基础上加随机偏移（±10 分钟），把"同时过期"变成"分散过期"。

```java
Random random = new Random();
long randomTime = random.nextLong(time - 10L, time + 10L);
this.set(key, r, randomTime, unit);
```

### 2.3 秒杀模块（项目最核心，面试价值最高）

**涉及文件：**
- `controller/VoucherOrderController.java`
- `service/impl/VoucherOrderServiceImpl.java`
- `resources/seckill.lua`
- `utils/RedisIDWorker.java`

**代码中保留了三种演进方案（旧版本为注释代码），展示了完整的技术迭代思路：**

| 版本 | 方案 | 问题 |
|------|------|------|
| V1（注释代码） | Java `synchronized` + 数据库直接操作 | 单机锁，分布式环境完全失效；数据库扛不住高并发 |
| V2（注释代码） | Lua 脚本原子操作 + Java 阻塞队列异步下单 | 阻塞队列在 JVM 内存中，服务重启丢失所有订单 |
| **V3（当前版本）** | **Lua 脚本 + Redis Stream 消息队列** | 当前最优方案 |

#### 2.3.1 V3 完整流程

```
用户请求 → Controller → Service.seckillVoucher()
    │
    ├── 1. RedisIDWorker 生成全局唯一订单 ID
    │
    ├── 2. 执行 seckill.lua（Redis 内原子操作）
    │       ├── 检查库存是否充足 → 不足 → 返回 1
    │       ├── 检查用户是否重复下单 → 重复 → 返回 2
    │       ├── 扣减库存 (incrby -1)
    │       ├── 记录用户已下单 (sadd)
    │       └── 发送消息到 Redis Stream (xadd) → 返回 0
    │
    └── 3. 后台线程 VoucherOrderHandler 异步消费
            ├── 从 stream.orders 读取消息 (XREADGROUP)
            ├── 创建数据库订单 (事务)
            ├── ACK 确认
            └── 异常时处理 Pending List (重试)
```

#### 2.3.2 seckill.lua 脚本详解

```lua
-- 1.参数列表
local voucherId = ARGV[1]   -- 优惠券id
local userId = ARGV[2]      -- 用户id
local orderId = ARGV[3]     -- 订单id

-- 2.数据key
local stockKey = "seckill:stock:" .. voucherId
local orderKey = "seckill:order:" .. voucherId

-- 3.脚本业务（以下操作在 Redis 内是原子的）
-- 3.1 判断库存是否充足
local stock = redis.call('get', stockKey)
if(not stock or tonumber(stock) <= 0) then
    return 1  -- 库存不足
end

-- 3.2 判断用户是否已下单
if(redis.call('sismember', orderKey, userId) == 1) then
    return 2  -- 重复下单
end

-- 3.3 扣库存
redis.call('incrby', stockKey, -1)

-- 3.4 记录用户已下单
redis.call('sadd', orderKey, userId)

-- 3.5 发送消息到队列中
redis.call('xadd', 'stream.orders', '*', 'userId', userId, 'voucherId', voucherId, 'id', orderId)

return 0  -- 成功
```

**为什么 Lua 脚本要放在 Redis 中执行？** 整个脚本在 Redis 服务端是原子执行的——判断库存、判断是否重复、扣库存、记录用户、发消息这五步操作是一个不可分割的整体。如果这五步用 Java 代码分步调用 Redis，在高并发下必然出现竞态条件（比如：线程 A 查库存还有 1，线程 B 也查库存还有 1，两个都扣减成功，超卖）。

**为什么用 Redis Stream 而不是 RabbitMQ/Kafka？** 项目已经用了 Redis，不需要额外部署消息中间件。Stream 的消费者组（Consumer Group）机制天然支持：
- 消息确认（ACK）：处理成功后确认，失败不确认
- Pending List：未确认的消息会进入 Pending List，`handlePendingList()` 方法会重新消费，保证消息不丢失
- 消费者组内负载均衡：多个消费者自动分摊消息

**为什么用 Redisson 分布式锁而不是自己写的 SimpleRedisLock？** `SimpleRedisLock` 只是教学演示用的基础实现。Redisson 的 `RLock` 提供了看门狗（Watchdog）机制——如果业务没执行完，锁会自动续期，不会因为超时而被误释放。而 `SimpleRedisLock` 的锁超时是固定的，一旦业务执行超过了 `timeoutSec`，锁会自动释放，可能造成其他线程获取到锁，导致并发安全问题。

#### 2.3.3 分布式 ID 生成器（RedisIDWorker）

采用 **时间戳 + 序列号** 的拼接策略：

```java
public Long nextId(String keyPrefix) {
    // 1. 生成时间戳（秒级，减去基准时间戳）
    LocalDateTime now = LocalDateTime.now();
    long nowSecond = now.toEpochSecond(ZoneOffset.UTC);
    long timestamp = nowSecond - BEGIN_TIMESTAMP;

    // 2. 生成序列号（Redis 自增，按天重置）
    String date = now.format(DateTimeFormatter.ofPattern("yyyyMMdd"));
    Long count = stringRedisTemplate.opsForValue().increment("icr:" + keyPrefix + ":" + date);

    // 3. 拼接：高 32 位时间戳 + 低 32 位序列号
    return timestamp << COUNT_BITS | count;
}
```

**优点：** 全局唯一、趋势递增（数据库索引友好）、高性能（不依赖数据库）、支持分布式。

### 2.4 探店笔记 + Feed 流模块

**涉及文件：**
- `controller/BlogController.java`
- `service/impl/BlogServiceImpl.java`
- `service/impl/FollowServiceImpl.java`

**功能清单：**

- 发布探店笔记、查看笔记详情
- 点赞/取消点赞（Redis ZSet 存储，按时间排序）
- 查看 Top 5 点赞用户
- 关注/取关用户（Redis Set 存储关注关系）
- 共同关注查询（Set 交集运算）
- **Feed 流推送**：发布笔记时推送给所有粉丝的收件箱（Redis ZSet，按时间戳排序）
- 滚动分页查询关注用户的笔记

**Feed 流设计（推模式）：**

用户 A 发布笔记 → 查询 A 的所有粉丝 → 将笔记 ID 推送到每个粉丝的 Redis ZSet 收件箱（`feed:{userId}`，score 为时间戳）。

查询时按时间倒序滚动分页，`reverseRangeByScoreWithScores` 天然支持滚动分页，解决了传统分页在数据实时变化时出现重复或遗漏的问题。

**为什么选推模式而不是拉模式？**
- 拉模式：用户查看 Feed 时，实时 JOIN 关注表和笔记表，按时间排序。当用户关注几百人时，SQL 性能很差。
- 推模式：写的时候扩散（发布笔记时推送给粉丝），读的时候只需查自己的收件箱，O(1) 复杂度。
- 对于中小规模平台，推模式的写扩散代价完全可接受。

### 2.5 AI 辅助模块

**涉及文件：** `controller/AiController.java`

**功能清单：**
- AI 生成笔记标题（`/ai/assist/title`）
- AI 润色笔记内容（`/ai/assist/polish`）
- AI 情感分析（`/ai/assist/sentiment`）

**设计要点：**

1. **为什么走 Java 转发而不是 nginx 直连？** 这些接口需要登录鉴权（发笔记本来就要登录）。`/ai/**` 不在 MvcConfig 白名单里，`LoginInterceptor` 天然拦截未登录请求，零配置获得鉴权。

2. **为什么用 Hutool 而不是 RestTemplate/WebClient？** pom 已有 hutool-all，零新增依赖。非流式转发不值得为此引入 WebClient/webflux。

3. **故障隔离**：Python 挂掉返回 `Result.fail("AI 服务暂不可用")`，前端体验不崩，排障时先 curl `/api/ai/health` 即可定位。

4. **30s 超时**：LLM 生成标题/润色可能要 5-15 秒，前端 axios 全局 5s 会被请求级覆盖，这里同样要放宽。

## 三、公共基础设施

### 3.1 分布式锁

项目中有两套分布式锁实现：

| 锁 | 用途 | 特点 |
|----|------|------|
| `SimpleRedisLock` | 教学演示 | SETNX + Lua 解锁，UUID 标识线程，无看门狗 |
| **Redisson RLock** | 生产使用 | 看门狗自动续期，可重入，功能完善 |

**unlock.lua 脚本：**

```lua
-- KEYS[1]: 锁的 key
-- ARGV[1]: 当前线程标识

if (redis.call('GET', KEYS[1]) == ARGV[1]) then
    -- 一致，则删除锁
    return redis.call('DEL', KEYS[1])
end
-- 不一致，则直接返回
return 0
```

这个脚本保证了"判断锁归属 + 删除锁"的原子性。如果不用 Lua 脚本，先 GET 判断再 DEL 是两个操作，中间可能被其他线程插入，导致误删别人的锁。

### 3.2 缓存客户端（CacheClient）

`CacheClient` 是项目的**缓存核心工具类**，封装了四种缓存策略：

| 方法 | 功能 | 解决什么问题 |
|------|------|-------------|
| `set()` | 普通缓存写入 | 基础 |
| `setWithLogicalExpire()` | 逻辑过期写入（存逻辑过期时间，不设物理 TTL） | 缓存击穿 |
| `queryWithPassThrough()` | 布隆过滤器 + 空值缓存查询 | 缓存穿透 |
| `queryWithLogicalExpire()` | 逻辑过期查询（过期返回旧数据，异步重建） | 缓存击穿 |

### 3.3 Token 刷新机制

`RefreshTokenInterceptor` 在每次请求时：

1. 从请求头取 Token（`authorization` header）
2. 从 Redis 查用户信息
3. 存入 `UserHolder`（ThreadLocal）
4. 刷新 Token 有效期（随机偏移防止同时过期）
5. 请求结束后（`afterCompletion`）清除 ThreadLocal，防止内存泄漏

### 3.4 全局异常处理

`WebExceptionAdvice` 使用 `@RestControllerAdvice` 统一捕获 `RuntimeException`，返回 `Result.fail("服务器异常")`，避免异常堆栈暴露给前端。

## 四、Redis Key 设计规范

| Key 前缀 | 数据结构 | 用途 | TTL |
|----------|----------|------|-----|
| `login:code:{phone}` | String | 验证码 | 2 min |

## 六、面试核心考点

### Q1：你们的秒杀系统是怎么设计的？怎么保证不超卖？

**回答思路（站在业务角度）：**

我们做的是一个旅游点评平台，商家会发布限时秒杀优惠券。秒杀的核心挑战是：**高并发下，库存扣减必须准确，不能超卖，也不能少卖。**

我们的方案是 **Lua 脚本 + Redis Stream 消息队列**：

1. **原子操作**：所有库存判断、扣减、用户重复下单校验都在一段 Lua 脚本中完成，Redis 执行 Lua 脚本是单线程原子的，天然线程安全。这就好比所有人在一个窗口排队，一个一个来，不会出现两个人同时拿到最后一张券的情况。

2. **异步下单**：Lua 脚本校验通过后，不直接写数据库，而是将订单消息发送到 Redis Stream 消息队列，立即返回"下单成功"给用户。后台有一个单独的线程异步消费消息，慢慢写数据库。这样数据库不会被瞬间的高并发请求打垮。

3. **消息可靠性**：Redis Stream 的消费者组机制支持 ACK 确认和 Pending List。如果订单处理失败，会从 Pending List 中重新消费，保证订单不丢失。

4. **分布式锁兜底**：异步下单时用 Redisson 分布式锁防止同一用户重复创建订单，作为最后一道防线。

---

### Q2：你们的缓存是怎么用的？怎么解决缓存的三个经典问题？

**回答思路：**

缓存是点评系统性能优化的核心，我们针对缓存穿透、击穿、雪崩分别做了处理：

**缓存穿透**（查不存在的数据）→ 布隆过滤器 + 空值缓存双保险。系统启动时把全量商铺 ID 加载到布隆过滤器，查询时先过一遍布隆——99% 的不存在 ID 在这一步就被拦截了。布隆过滤器误判的那 1%，由空值缓存兜底（缓存一个空字符串，2 分钟过期）。

**缓存击穿**（热点数据过期）→ 逻辑过期。不设物理 TTL，而是存一个逻辑过期时间。过期了也先返回旧数据给用户，只让一个线程异步去更新。这样用户感知不到任何延迟，尤其适合商铺详情这种"读多写少"的场景。

**缓存雪崩**（大量缓存同时过期）→ TTL 随机化。给每个缓存的过期时间加一个随机偏移（±10 分钟），把"同时过期"变成"分散过期"，避免数据库瞬间压力。

---

### Q3：为什么订单 ID 不用数据库自增，而要自己写一个 RedisIDWorker？

**回答思路：**

数据库自增 ID 在秒杀场景下有两个问题：

1. **性能瓶颈**：每次插入都要等数据库返回自增 ID，高并发下数据库压力大。
2. **分布式扩展**：如果将来分库分表，自增 ID 会冲突。

我们的 RedisIDWorker 是雪花算法思路的简化版：高 32 位是秒级时间戳，低 32 位是 Redis 当天自增序列号。这个方案的好处是：
- **全局唯一**：不同服务实例生成的 ID 不会冲突
- **趋势递增**：对数据库索引友好
- **高性能**：ID 生成完全在 Redis 完成，不依赖数据库

---

### Q4：为什么你们的 Feed 流用 Redis ZSet 而不是直接查数据库？

**回答思路：**

Feed 流（关注的人发布的笔记）如果用数据库实现，需要 JOIN 关注表和笔记表，然后按时间排序分页。当用户关注了几百人，笔记量上万时，这个 SQL 会非常慢。

我们的方案是**推模式**：用户发布笔记时，把笔记 ID 推送到所有粉丝的 Redis ZSet 收件箱（score 是时间戳）。用户查看 Feed 时只需要查自己的收件箱，复杂度从 O(n) 降到 O(1)。而且 ZSet 的 `reverseRangeByScore` 天然支持滚动分页，解决了传统分页在数据实时变化时出现重复的问题。

推模式的代价是写扩散（一个百万粉丝的大 V 发笔记，要写百万条数据），但对于我们这个阶段的中小规模平台，这个代价完全可接受。

---

### Q5：你们的登录方案是怎么设计的？为什么不用 Session？

**回答思路：**

传统 Session 方案的问题在于：Session 存储在服务器内存中，多台服务器之间无法共享，做负载均衡时用户会频繁掉线。

我们的方案是 **Redis + Token**：
- 用户登录后，生成一个随机 Token，将用户信息存入 Redis（Hash 结构），返回 Token 给前端
- 前端每次请求在 Header 中携带 Token
- 后端用 **双拦截器链**：`RefreshTokenInterceptor` 负责刷新 Token 有效期（每次请求自动续期），`LoginInterceptor` 负责鉴权拦截
- 用 ThreadLocal 存储当前请求的用户信息，请求结束后清理

这个方案的好处是：无状态、可水平扩展、Token 有效期自动续期，用户体验好。

---

### Q6：你们项目中 AI 功能是怎么集成的？为什么 Java 只做转发？

**回答思路：**

AI 功能（生成标题、润色、情感分析）的实际计算由 Python 服务完成，因为 Python 生态有 LangChain、Transformers 等成熟的 AI 库。Java 后端只做 HTTP 转发，相当于一个"网关"。

**为什么走 Java 转发而不是前端直连 Python？** 因为这些 AI 接口需要登录鉴权——用户发笔记本来就要登录，Java 的拦截器链天然拦截未登录请求，零额外配置。如果前端直连 Python，需要在 Python 侧再实现一套鉴权逻辑，增加系统复杂度。

**故障隔离**：Python 挂了只影响 AI 功能，返回"AI 服务暂不可用"，不影响商铺浏览、秒杀下单等主流程。

---

### Q7：什么是布隆过滤器？你们项目中怎么用的？

**回答思路：**

布隆过滤器是一种概率型数据结构，用于快速判断"一个元素是否**一定不存在**于集合中"。它的特点是：
- 如果布隆过滤器说"不存在"，那一定不存在（100% 准确）
- 如果布隆过滤器说"存在"，那可能不存在（有误判率，我设的是 1%）

我们在项目中用它来拦截对不存在商铺 ID 的查询请求。项目启动时，`BloomFilterInitializer` 通过 `ApplicationRunner` 自动把数据库中所有商铺 ID 加载到布隆过滤器。查询时先过布隆——99% 的无效请求在这一步就被拦截了。误判的 1% 由空值缓存兜底。

**为什么选择布隆过滤器？** 内存效率极高——100 万条数据只需要几 MB。如果用 Set 存，需要几十 MB 甚至更多。

---

### Q8：Redis 和 MySQL 怎么保证数据一致性？

**回答思路：**

在我们的项目中，缓存和数据库的数据一致性方案取决于业务场景：

1. **商铺信息**：采用 **Cache Aside 模式**——更新数据库时删除缓存，下次查询时重建。因为我们用的是逻辑过期方案，所以即使短暂不一致，最多 30 秒后就会自动更新。

2. **秒杀库存**：库存以 Redis 为准，Lua 脚本原子扣减。数据库的库存是最终一致——异步下单时写入。这是"最终一致性"策略，因为秒杀场景下性能和准确性比实时一致性更重要。

3. **点赞/关注**：先更新数据库，再更新 Redis。如果 Redis 更新失败，下次查询时会从数据库重新加载。

## 七、总结

长安点评项目是一个**典型的 Spring Boot + Redis 实战项目**，涵盖了互联网后端开发的核心技术栈：

- **高并发**：秒杀系统（Lua 原子操作 + Redis Stream 异步削峰）
- **高性能**：多级缓存策略（布隆过滤器、逻辑过期、TTL 随机化）
- **高可用**：分布式锁（Redisson）、消息可靠性（ACK + Pending List）
- **分布式**：分布式 ID 生成、Redis 会话管理
- **业务场景**：Feed 流推送、GEO 附近搜索、Bitmap 签到、AI 集成

代码中保留了多种方案的演进痕迹（注释掉的旧版本），非常适合作为实习简历中的亮点项目——不仅有完整业务功能，更有对缓存、并发、分布式等核心问题的深入思考和解决方案。
