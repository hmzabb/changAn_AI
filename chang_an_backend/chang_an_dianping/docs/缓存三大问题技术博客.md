# Redis 缓存穿透/击穿/雪崩：从业务角度讲透技术选型（附面试话术）

> 我在做点评系统时，缓存命中率一直上不去，数据库动不动就告警。排查后发现踩了 Redis 的三个经典大坑。这篇文章用实际项目代码，把问题和解法讲清楚。

---

## 事故现场

这是我最初写的商铺查询接口：

```java
public Shop queryById(Long id) {
    String key = "cache:shop:" + id;
    String json = stringRedisTemplate.opsForValue().get(key);
    if (json != null) return JSON.parseObject(json, Shop.class);
    
    // Redis 没命中 → 直接查 MySQL
    Shop shop = getById(id);
    stringRedisTemplate.opsForValue().set(key, JSON.toJsonString(shop), 30, TimeUnit.MINUTES);
    return shop;
}
```

**看似没问题，但"缓存没命中"有三种致命情况，我一种都没处理。**

## 第一坑：缓存穿透

### 问题本质

查询**根本不存在的数据**，Redis 和 MySQL 都查不到，每次请求都穿透到数据库。

**业务场景**：长安旅行平台刚上线时，有人用爬虫工具批量请求 `id=-1`、`id=999999` 这种不存在的商铺 ID。由于没有任何防护，这些请求全部打到 MySQL，导致数据库 CPU 飙升到 90%，正常用户打开商铺列表直接超时。

### 业务决策：为什么选布隆过滤器 + 空值兜底？

**我的项目选择**：布隆过滤器（第一道防线）+ 缓存空值（第二道防线）。

**业务考量**：
- **双层防护更安全**：布隆过滤器能拦截 99% 的不存在 ID 请求，根本不会打到数据库；但布隆过滤器有误判率（我设的 1%），所以需要空值缓存兜底，防止那 1% 的误判请求穿透
- **开发成本可控**：Redisson 已经引入了，布隆过滤器只需要几行代码初始化；空值缓存更是零成本
- **业务容忍度**：布隆过滤器初始化时需要加载所有 shopId，新商铺上线需要同步更新，但这个延迟在可接受范围内

**为什么不只用空值缓存？**
> 如果只用空值缓存，恶意攻击者用随机 ID 刷接口，会生成大量空 key 占用 Redis 内存。布隆过滤器用极小内存（100 万数据只要几 MB）就能拦截绝大部分请求，空值缓存只作为兜底，两者配合最优。

### 完整实现：布隆过滤器 + 空值兜底

```java
public Shop queryWithPassThrough(Long id) {
    String key = "cache:shop:" + id;
    
    // 第一道防线：布隆过滤器拦截
    if (!bloomFilter.contains(id)) {
        return null;  // 一定不存在，直接返回
    }
    
    // 第二道防线：缓存查询（包括空值）
    String json = stringRedisTemplate.opsForValue().get(key);
    if (json != null) {
        // 空字符串说明是空值缓存，直接返回 null
        if ("".equals(json)) return null;
        return JSON.parseObject(json, Shop.class);
    }
    
    // 查数据库
    Shop shop = getById(id);
    
    // 数据库也没查到 → 缓存空值兜底
    if (shop == null) {
        stringRedisTemplate.opsForValue().set(key, "", 2, TimeUnit.MINUTES);
        return null;
    }
    
    // 查到了 → 正常缓存
    stringRedisTemplate.opsForValue().set(key, JSON.toJsonString(shop), 30, TimeUnit.MINUTES);
    return shop;
}
```

**关键点**：
- 布隆过滤器初始化：项目启动时加载所有 shopId
- 新商铺上线：运营后台创建商铺时，同步添加到布隆过滤器
- 空值 TTL 设短（2 分钟），避免正常数据写入后缓存还是空的

## 第二坑：缓存击穿

### 问题本质

**热点数据**缓存过期瞬间，大量请求同时查数据库。

**业务场景**：国庆假期期间，长安钟楼、回民街这些热门商铺的访问量暴增。这些商铺的缓存 30 分钟过期，过期那一刻，2000 个用户的请求同时打到 MySQL，数据库连接池瞬间被打满，所有商铺接口全部超时，用户看到的就是"加载失败"。

### 业务决策：为什么选逻辑过期？

**我的项目选择**：逻辑过期方案。

**业务考量**：
- **用户体验优先**：旅行点评平台的核心是"让用户流畅地浏览商铺"。如果用互斥锁，缓存过期时 1999 个用户要等待几百毫秒甚至更久才能拿到响应，页面会卡顿。逻辑过期能立刻返回旧数据，用户感知不到任何延迟
- **数据一致性要求不高**：商铺信息（名称、地址、评分）不会频繁变更，即使返回的是 30 秒前的旧数据，对用户决策几乎没有影响。用户不会因为商铺评分差了 0.1 分就投诉
- **高并发场景**：节假日流量高峰时，互斥锁会让大量线程阻塞等待，反而增加响应时间。逻辑过期完全不阻塞，吞吐量更高

**什么时候我会选互斥锁？**
> 如果是订单状态、库存数量这种场景，用户看到旧数据会导致重复下单或超卖，就必须用互斥锁保证强一致性。但在商铺浏览场景，流畅体验比数据实时性更重要。

### 解法一：互斥锁（强一致性场景备选）

```java
public Shop queryWithMutex(Long id) {
    String key = "cache:shop:" + id;
    String lockKey = "lock:shop:" + id;
    String json = stringRedisTemplate.opsForValue().get(key);
    
    // 1. 命中缓存
    if (StrUtil.isNotBlank(json)) {
        return JSON.parseObject(json, Shop.class);
    }
    
    // 2. 没命中 → 尝试获取分布式锁
    try {
        Boolean lock = stringRedisTemplate.opsForValue()
            .setIfAbsent(lockKey, "1", 10, TimeUnit.SECONDS);
        
        if (lock == null || !lock) {
            // 获取锁失败 → 等待后重试
            Thread.sleep(50);
            return queryWithMutex(id);  // 递归重试
        }
        
        // 3. 获取锁成功 → 查数据库重建缓存
        Shop shop = getById(id);
        Thread.sleep(200);  // 模拟重建耗时
        stringRedisTemplate.opsForValue().set(key, JSON.toJsonString(shop), 30, TimeUnit.MINUTES);
        
        return shop;
    } catch (InterruptedException e) {
        throw new RuntimeException(e);
    } finally {
        // 4. 释放锁（用 Lua 脚本保证原子性）
        stringRedisTemplate.delete(lockKey);
    }
}
```

### 解法二：逻辑过期（我的项目方案）

```java
@Data
class RedisData {
    private LocalDateTime expireTime;
    private Object data;
}

// 写入缓存时：设置逻辑过期时间，不设物理 TTL
public void setWithLogicalExpire(String key, Object data, Long expireSeconds) {
    RedisData redisData = new RedisData();
    redisData.setData(data);
    redisData.setExpireTime(LocalDateTime.now().plusSeconds(expireSeconds));
    stringRedisTemplate.opsForValue().set(key, JSON.toJsonString(redisData));
}

// 查询时：过期了也先返回旧数据，异步更新
public Shop queryWithLogicalExpire(Long id) {
    String key = "cache:shop:" + id;
    String json = stringRedisTemplate.opsForValue().get(key);
    
    if (StrUtil.isBlank(json)) return null;
    
    RedisData redisData = JSON.parseObject(json, RedisData.class);
    LocalDateTime expireTime = redisData.getExpireTime();
    
    // 1. 没过期 → 直接返回
    if (expireTime.isAfter(LocalDateTime.now())) {
        return (Shop) redisData.getData();
    }
    
    // 2. 过期了 → 尝试获取锁，异步更新
    String lockKey = "lock:shop:" + id;
    Boolean lock = stringRedisTemplate.opsForValue().setIfAbsent(lockKey, "1", 10, TimeUnit.SECONDS);
    
    if (lock != null && lock) {
        // 获取锁成功 → 提交异步任务更新缓存
        CACHE_REBUILD_EXECUTOR.submit(() -> {
            try {
                Shop shop = getById(id);
                setWithLogicalExpire(key, shop, 30L);
            } catch (Exception e) {
                log.error("重建缓存失败", e);
            } finally {
                stringRedisTemplate.delete(lockKey);
            }
        });
    }
    
    // 3. 无论是否获取锁，都先返回旧数据
    return (Shop) redisData.getData();
}
```

**两种方案对比**：

| 方案 | 一致性 | 性能 | 适用场景 |
|------|--------|------|---------|
| 互斥锁 | 强一致 | 低（其他线程等待） | 订单、库存、支付 |
| 逻辑过期 | 最终一致 | 高（不阻塞） | 商铺、文章、商品详情 |

## 第三坑：缓存雪崩

### 问题本质

**大量缓存同时过期**，请求全部打到数据库。

**业务场景**：运营团队为了国庆活动，一次性批量导入了 1000 个新商铺。我给这些商铺统一设置了 30 分钟的 TTL。结果 30 分钟后，这 1000 个商铺的缓存同时过期，正好赶上晚高峰用户浏览，数据库瞬间承受了平时 10 倍的查询压力，直接报警。

### 业务决策：为什么选 TTL 随机化 + 缓存预热？

**我的项目选择**：TTL 随机化（基础）+ 缓存预热（根本）。

**业务考量**：
- **TTL 随机化**：这是最低成本的改动，只需要在设置缓存时加一行随机数代码。虽然不能从根本上解决问题，但能把"同时过期"变成"分散过期"，大幅降低数据库瞬间压力
- **缓存预热**：旅行平台有明显的"热点效应"——钟楼、大雁塔、回民街这些商铺 80% 的流量集中在 20% 的商铺上。与其等缓存过期了被动重建，不如系统启动时就把这些热点数据提前加载好。这样即使用户一打开 App 就能看到数据，不用等待缓存重建
- **多级缓存没选的原因**：引入 Caffeine 本地缓存会增加架构复杂度，而且本地缓存和 Redis 之间的数据同步是个麻烦事。对于初期项目，TTL 随机化 + 预热已经足够

**如果业务规模扩大了怎么办？**
> 当日活达到百万级，单台 Redis 扛不住时，就需要多级缓存架构：Caffeine 扛第一波流量，Redis 扛第二波，数据库兜底。但在当前阶段，过度设计反而增加维护成本。

### 解法一：TTL 加随机值（基础方案）

```java
// 原来：同时过期
redis.set(key, data, 30, TimeUnit.MINUTES);

// 现在：20~40 分钟随机分布
long ttl = 30 + ThreadLocalRandom.current().nextLong(-10, 11);  // [20, 40] 分钟
stringRedisTemplate.opsForValue().set(key, data, ttl, TimeUnit.MINUTES);
```

### 解法二：多级缓存（进阶方案）

```java
// 一级缓存：Caffeine（本地，5分钟）
// 二级缓存：Redis（分布式，30分钟+随机）
// 两级 TTL 错开，不会同时失效
```

### 解法三：缓存预热（根本方案）

```java
// 系统启动时，提前加载热点数据到 Redis
@PostConstruct
public void warmUpCache() {
    List<Shop> hotShops = shopMapper.selectHotShops();
    for (Shop shop : hotShops) {
        long ttl = 30 + ThreadLocalRandom.current().nextLong(-10, 11);
        stringRedisTemplate.opsForValue()
            .set("cache:shop:" + shop.getId(), JSON.toJsonString(shop), ttl, TimeUnit.MINUTES);
    }
}
```

## 面试速答

**Q：缓存穿透和缓存击穿的区别？**
> 穿透是查**不存在的数据**，用布隆过滤器或缓存空值解决；击穿是**热点数据缓存过期**，大量请求同时查库，用互斥锁或逻辑过期解决。

**Q：布隆过滤器的原理？能删除吗？**
> 用多个哈希函数将元素映射到位数组，查询时所有位为 1 才认为存在。**不能删除**，因为多个元素共享位，删除会影响其他元素。可改用 Counting Bloom Filter。

**Q：互斥锁方案中，释放锁为什么用 Lua 脚本？**
> 判断锁是否是自己持有的 + 删除锁，这两个操作必须原子执行。如果分开执行，可能判断完后锁过期了，误删了别人新加的锁。

```lua
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

**Q：缓存和数据库双写一致性怎么保证？**
> 采用 **Cache Aside Pattern**：先更新数据库，再删除缓存。读取时缓存不存在再重建。删除比更新更安全，避免并发写入导致脏数据。

**Q：Redis 分布式锁怎么实现？**
> 用 `SET key value NX PX timeout` 命令，NX 保证只在 key 不存在时设置，PX 设置过期时间防死锁。生产环境推荐用 **Redisson**，内置看门狗自动续期、可重入锁等特性。

## 实习面试延伸问题

### Q1：你的项目中缓存是怎么设计的？

> 在长安旅行点评系统中，我根据**业务场景**设计了不同的缓存策略：
> 
> - **商铺详情**：用逻辑过期方案。因为这是高频浏览场景，用户打开 App 就要看到商铺信息，**流畅体验比数据实时性更重要**。商铺信息（名称、地址、评分）变更频率低，即使返回 30 秒前的旧数据也不影响用户决策
> - **用户信息**：用互斥锁方案。因为涉及订单、支付等场景，**数据一致性要求高**，用户不能看到旧的余额或订单状态
> - **验证码**：设置固定 TTL。因为是一次性数据，过期就失效，不需要复杂的缓存策略
> 
> 同时做了 TTL 随机化防止雪崩，对不存在的 key 缓存空值防止穿透。

### Q2：为什么商铺场景选逻辑过期而不是互斥锁？

> 这是基于**业务权衡**的选择：
> 
> - **用户体验**：互斥锁会让 99% 的请求阻塞等待，页面会卡顿。逻辑过期立刻返回旧数据，用户感知不到延迟
> - **数据特性**：商铺信息变更频率低（一天可能改几次），30 秒的数据延迟完全可接受
> - **流量特征**：节假日流量高峰时，互斥锁反而会成为瓶颈，逻辑过期吞吐量更高
> 
> 但如果是库存、订单这种场景，我会毫不犹豫选互斥锁，因为数据不一致会导致超卖或资损。

### Q3：如果 Redis 挂了怎么办？

> 分层考虑：
> - **短期兜底**：本地缓存（Caffeine）扛一小段时间
> - **中期高可用**：Redis 集群 + 哨兵模式，主节点挂了自动切换
> - **长期架构**：多级缓存 + 服务降级，Redis 挂了限流保护数据库

### Q4：缓存预热怎么做？

> - 系统启动时通过 `@PostConstruct` 加载热点数据
> - 定时任务定期刷新热点数据
> - 消息队列监听数据变更，主动更新缓存
> 
> 在我们项目中，运营后台新增商铺时，会发一条 MQ 消息，缓存服务监听到后主动预热，而不是等用户请求来了才加载。

### Q5：如果让你重新设计这个缓存方案，你会怎么改进？

> 基于当前业务发展，我会做三个改进：
> 
> 1. **引入 Caffeine 本地缓存**：把最热的 100 个商铺放在本地，减少 Redis 网络开销
> 2. **缓存监控告警**：监控缓存命中率、重建频率，命中率低于 80% 就告警
> 3. **动态 TTL 策略**：根据商铺访问量动态调整 TTL，热点商铺 TTL 更长，冷门商铺 TTL 更短
